# 架构详解

## 设计目标

这套工作流把调度、任务读取、Agent 处理和知识沉淀拆成四层。每一层只承担一种职责，可以单独替换和测试。

## 四层结构

### 调度层

调度层负责在固定时间触发命令。它可以是 Hermes Cron、Windows 任务计划程序、GitHub Actions 或其他调度器。公开示例只描述任务名称、时间和入口命令，不保留生产提示词。

### 数据接入层

`dida_undone.py` 通过本地 CLI 按项目读取未完成任务。项目清单从 `DIDA_PROJECTS_JSON` 注入。

`dida_completed_mcp.py` 通过滴答官方 MCP 获取指定日期的已完成任务，再按 `completedTime` 在本地过滤和去重。

### Agent 处理层

四个 Skills 分别负责启动前澄清、执行检查、任务拆分和 Notion 写入。它们只定义通用操作规则，不保存用户画像、公司背景或个人目标。

### 沉淀层

`notion_api.py` 封装 Notion API 的读取、创建、追加和归档操作。`notion_bridge.py` 负责生成复盘 Markdown，并选择日记页或复盘总页作为父页面。

## 数据流与信任边界

```text
Cron
  |
  v
滴答 CLI / MCP ----> 任务 JSON
                         |
                         v
                    AI Agent + Skills
                         |
                         v
                    复盘 Markdown
                         |
                         v
                    Notion API
```

环境变量位于信任边界内。日志、示例、文档和 Git 仓库位于边界外，因此不得写入真实 token、页面 ID、项目 ID 或任务正文。

## 失败处理

- 环境变量缺失时立即停止，并提示缺少的变量名。
- CLI 返回非零状态时保留简短错误信息，不继续解析错误输出。
- API 返回错误时只输出状态码和截断后的响应，不输出请求头。
- 日期解析失败时拒绝执行，避免查询错误窗口。
- Notion 写入默认先支持 `--dry-run`，让使用者确认 Markdown 后再提交。

## 可替换点

- 将 Hermes Cron 换成 Windows 任务计划程序，不影响脚本。
- 将滴答换成其他任务系统，只需重写数据接入层。
- 将 Notion 换成本地 Markdown 或其他知识库，只需重写沉淀层。
- 将模型或 Agent 框架替换，不影响凭据隔离和调度结构。

## 隐私原则

公开仓库展示方法和接口边界，不展示生产数据。运行证据通过脱敏后的规模描述、合成示例和可执行代码体现，原始日志不作为作品集材料。
